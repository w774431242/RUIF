一 · 消费 Mod 如何调用 RUIF

RUIF 是框架 Mod（与 Harmony / HugsLib 同模式）：玩家订阅 RUIF Mod 后，游戏启动即加载全游戏唯一的 RUIF.dll；你的 Mod 只引用、不内嵌。当前版本 v1.0.1，公共 API 全量清单见随包 DevDocs/API参考.md（自动生成：73 个公开类型 / 435 个公开成员）。

第一步不是写代码，是选依赖模式 —— 二选一，混用就是"假降级"：
模式About.xml探测方式适合
硬依赖（推荐）写 modDependencies + loadAfter直接调 RUIF.Api.IsAvailable(minVersion)，只做版本门控没有框架就没有意义的功能
软依赖不写 modDependencies，只写 loadAfter反射扫 AppDomain 找 RUIF.Api；所有 RUIF 调用隔离到独立类型，方法标 [MethodImpl(NoInlining)]有原生兜底路径的功能
为什么不能"声明硬依赖 + 又写 else 降级"：RUIF.Api 类型本身就在 RUIF.dll 里。框架缺失时，任何会被 JIT 的代码路径出现 Api.Xxx，就会在方法编译阶段抛 FileNotFoundException / TypeLoadException——try/catch 拦不住，你的 else 分支永远不会执行。这不是风格问题，是"降级到底有没有发生过"的问题。
1
硬依赖：About.xml 声明依赖 —— 玩家未启用 RUIF 时，游戏会在 Mod 列表明确提示，而不是让 UI 静默炸掉： 
<modDependencies>
  <li>
    <packageId>PersonalChronicle.RUIFramework</packageId>
    <displayName>RUI Framework</displayName>
  </li>
</modDependencies>
<loadAfter>
  <li>PersonalChronicle.RUIFramework</li>
</loadAfter>
此时框架必然已加载，IsAvailable 只剩下"够不够新"这一个问题： 
// Mod 类构造器
public MyMod(ModContentPack content) : base(content)
{
    if (!RUIF.Api.IsAvailable("1.0"))
        Log.Warning("[MyMod] RUIF 版本过低，界面降级为原生 Widgets。");
}
2
csproj 引用 RUIF.dll（不随包分发） —— <Private>false</Private> 确保你的发布包 Assemblies 里没有 RUIF.dll（内嵌会与其他 Mod 的副本冲突）： 
<Reference Include="RUIF">
  <HintPath>路径/RUIF/Assemblies/RUIF.dll</HintPath>
  <Private>false</Private>
</Reference>
3
软依赖：探测用反射，调用要隔离 —— 主路径（构造器 / Update / 静态构造）不得出现任何 RUIF 类型： 
// ① 探测：只用字符串 + 反射。本类型不引用 RUIF，所以框架缺失时它照样能加载
bool available = false;
foreach (var a in AppDomain.CurrentDomain.GetAssemblies())
    if (a.GetName().Name == "RUIF")
    {   // a.GetType("RUIF.Api") → GetMethod("IsAvailable").Invoke(null, new object[] { "1.0" })
        available = true;
    }

// ② 隔离：唯一允许出现 RUIF 类型的地方，方法必须 NoInlining
//    否则 JIT 可能把调用内联进调用方 → 调用方在编译期就需要 RUIF 类型 → 照样抛异常
[MethodImpl(MethodImplOptions.NoInlining)]
static void OpenMyWindow() => Find.WindowStack.Add(new Dialog_MyWindow());
框架不再随包附带可编译模板工程（旧 Sample/ 已随换肤层移除）；软依赖的探测 / 隔离写法见上，绘制写法见 §二。
降级是实机结论，不是纸面兜底：软依赖模式下，UI 代码按「数据准备」与「绘制」分离，绘制层只读一个你缓存的 bool（RUIF 路径 / Listing_Standard 原生路径）。禁用 RUIF 后仍能启动、能操作，才算降级成立；没实机测过就在文档里写 NOT RUN，不许写"已降级"。

〇 · 先澄清：RUIF 是"预设实例"吗？

答：第三方 Mod 直接调用（普通程序集引用，编译期引用 dll + 运行期游戏加载唯一一份，像调 Harmony 一样 using RUIF;）。但 RUIF 预设的是令牌 / 度量 / 组件行为规范，不是预设 UI 实例——UI 结构由每个 Mod 在自己的绘制代码里声明。三种东西归属不同：
东西归属要点
无状态组件（Button/Card/Pill…，Minimal/Advanced）RUIF 提供 API，无实例即时模式：每帧调用当帧绘制，数据你传
有状态组件（Table/Selection…，Expert）你 new、你持有实例存你 Mod 类的字段；别存 Window 里（窗口关掉即弃）
全局静态（RUIF.Api / 只读令牌 RUIF.Tokens）RUIF 全局静态唯一"预设"的部分；令牌为固定只读值，框架不含可切换主题

二 · 最小可用示例（真实签名）

一个标准原版窗口内调用 RUIF —— Window 仍是原版类型，RUIF 只接管 DoWindowContents 里的布局与绘制。下面每个调用都对应 API参考.md 里的真实签名（本示例已编译通过）：

public class Dialog_Example : Window
{
    public override Vector2 InitialSize => new Vector2(520f, 420f);

    public override void DoWindowContents(Rect inRect)
    {
        // L4 布局：只声明结构，Rect 由框架算（struct 游标，零堆分配；超出容器自动裁剪）
        var col = RUIF.Layout.Column(inRect, RUIF.Tokens.SpaceSm);
        Rect head = col.Take(30f);

        // L1 令牌 + L2 原子：颜色一律取自 Tokens，绝不裸写 new Color / 裸改 GUI.color
        RUIF.Draw.Label(head, "例示窗口", RUIF.Tokens.FontValue, RUIF.Tokens.Text, TextAnchor.MiddleLeft);

        Rect body = RUIF.Atoms.SectionFrame(col.Rest, "Example");
        Rect card = RUIF.Layout.Inset(body, RUIF.Tokens.CardPadX, RUIF.Tokens.CardPadY);
        RUIF.Draw.Box(card, RUIF.Tokens.Card);
        RUIF.Draw.Border(card, RUIF.Tokens.BorderSoft);
        RUIF.Draw.Label(card, "内容画在你的 DoWindowContents 里", RUIF.Tokens.FontBody, RUIF.Tokens.Text, TextAnchor.MiddleLeft);
    }
}
状态（v1.0.0）：本示例的每个 API 都存在于 DevDocs/API参考.md（该清单由 _scripts/gen_api_reference.ps1 反射生成，与 dll 同源），并已在框架源码工程内编译通过。
仍未做的：using (var col = RUIF.VStack(...)) 式布局 DSL 与链式 .Tip().OnClick()（见 §三）——那是 I0 的设计承诺，v1.0.0 未实施，不要据此编码。

三 · 三档 API（设计承诺 · 尚未实施）

⚠️ 现存差异（必读）：下表是 I0 期的接口设计意图，v1.0.0 尚未实施。当前实际 API 是静态方法 + struct 布局游标（RUIF.Layout.Column(rect, gap) → VStack.Take(h)；组件为静态方法，数据由调用方注入），没有顶层 Button(...) 快捷函数，也没有链式 .Tip().Disabled().OnClick()。
编码唯一依据 = DevDocs/API参考.md；本节保留原文只为让"接口设计意图"可追溯，不要据此写代码。

四 · 配色与本地化

配色（框架不含换肤引擎）

框架不提供主题注册 / 运行时换肤：旧 Theme.Register / Theme.Apply 系列 API 已于 v1.0.0 公开发布前整体移除。外观颜色一律取只读令牌 RUIF.Tokens.*。想在组件之外使用自定义配色，就在你自己的 Mod 里持有颜色常量并自行管理，不要把框架令牌当作可切换主题。

本地化约定

  • 组件 API 一律收已翻译字符串：你传 "MyMod.Title".Translate() 的结果，框架不替你做翻译决策；
  • 框架组件自身不产出面向玩家的文案；若有则走框架 Mod 的 Languages 目录（Keyed）。

五 · 发布检查清单（消费 Mod 视角）

项要求
RUIF.dll发布包 Assemblies 内不得内嵌（csproj Private=false，发版前检查一次）
依赖模式二选一：硬依赖（写 modDependencies）或软依赖（不写 modDependencies，只写 loadAfter）—— 不要混着来
版本断言硬依赖：构造器调 RUIF.Api.IsAvailable(minVersion)；软依赖：反射探测 + 结果缓存到你自己的静态字段
降级实测禁用 RUIF 后你的 Mod 仍可加载、可操作（实机测；没测过就在文档标 NOT RUN，不许写"已降级"）
绘制态纪律你的窗口代码不裸改 GUI.color / Text.Font；一切经 RUIF 组件或 Draw.*Scope（Draw.Color/Font/Anchor 等）
数据纪律传给组件的是已准备好的纯数据；排序 / null-guard 在你的代码里做，不指望框架

六 · 引擎可行性审计（逐项，不粉饰）

审计方法（可复核）：结论依据三类证据——① 知识库核实的原版 API 面（§38 UI 类型族：Window / Widgets / Listing_Standard / TooltipHandler 等）；② PersonalChronicle 参考实现 400+ 处实机调用与多轮实机验收；③ 反编译工具（ilspycmd）对目标 Build 程序集的核实（如 1.6 DrawBoxSolid 会重置 GUI.color、CompPower 链式模型等均由此定案）。RUIF 编码期每个 API 落地前都会走同样的反编译核实，不以记忆为准。

✅ 100% 引擎原生——零妥协，全部是引擎公开 API 的现成能力

能力实现依据
文本绘制 / 测量 / 宽度截断Verse.Text（Font 三档 / CalcSize / Anchor）——原版界面同机制
按钮 / 复选 / 滑条 / 输入框 / 单选Widgets.ButtonText / Checkbox / HorizontalSlider / TextField / Listing_Standard.RadioButton
面板 / 卡片 / 描边 / 分隔线 / 高亮 / 徽标DrawBoxSolid / DrawBox / DrawLineHorizontal / DrawLineVertical / DrawHighlight* 组合
进度条Widgets.FillableBar + 自绘双轨（参考实现两种都在用）
滚动 / 大列表虚拟化BeginScrollView + 可见行数学——原版列表同模式，非黑科技
TooltipTooltipHandler.TipRegion + TipSignal（第二参=延迟秒）
贴图染色（自定义配色）ContentFinder<Texture2D> 懒加载 + GUI.color 乘法染色——引擎官方机制（框架不自带换肤层）
程序动画（渐变 / 滑入 / 呼吸态）IMGUI 每帧重绘，Time 插值即动画——100% 代码可实现；流畅度受游戏帧率制约（战斗掉帧时 UI 动画同步掉帧，如实告知）
右键 / 悬停 / 键盘事件Event.current（button==1 右键已在参考实现 ClickableCard 实测）、Mouse.IsOver、窗口键盘事件

⚠️ 可实现，但有代价——如实标注代价，绝不按 ✅ 宣传

能力实现方式代价 / 边界
圆角 / 阴影 / 描边特效预渲染 NinePatch PNG 贴图（引擎无矢量圆角）随 Mod 发素材；RUIF 默认直角——直角即原生，圆角即素材，文档会标明每个组件用的是哪种
自定义字体官方路径 = AssetBundle（1.6 明确支持 Shader/Font/Mesh 走 bundle；松散 TTF 无官方加载路径）需构建 bundle 管线，字体改动要重建 bundle；与原版 Text 管线的兼容性须先做原型验证——原型通过前，RUIF 只承诺原版三档字体
曲线 / 图表折线逼近（DrawLine 分段）分段数有上限（GC / draw call）；不做平滑贝塞尔插值渲染
图标体系消费 Mod 自备贴图，或复用原版 Textures/UI 资产框架不内置图标库（避免替所有 Mod 定图标审美）
零分配纪律布局缓存 + Dirty 标记 + 对象复用违反纪律（每帧 new List / LINQ / 闭包）会 GC 卡顿——框架会提供安全路径，但拦不住你在绘制回调里乱分配

❌ 引擎层面做不到——RUIF 明确不承诺，文档与宣传永不越线

做不到的原因
React 式保留模式 / 虚拟 DOM 自动 diff引擎是即时模式（每帧重绘、无保留控件树）。RUIF 用「布局算一次 + Dirty 复用」逼近其收益，但不是自动 diff——这是设计定调，不是技术缺陷
实时高斯模糊 / 后处理合成UI 层无 RenderTexture 后处理管线的合理成本路径；理论可行但每帧开销不可接受——不做
系统原生控件（系统文件对话框等）只能用游戏自带 Dialog 体系
多线程 UIIMGUI 主线程独占；后台线程只能准备数据，不能碰绘制
触摸 / 手势桌面版只有鼠标 + 键盘
松散 TTF 字体加载本项目实测不可靠（无 byte[] Font 构造、OS 字体切换脆弱）——官方路径只剩 AssetBundle（见 ⚠️ 行）

七 · 不失真承诺（写进框架文档的硬规矩）

  1. 三级标注制：RUIF 每个组件的文档页固定显示实现等级徽标（✅ 原生 / ⚠️ 有代价+代价说明 / ❌ 不做）。⚠️ 永不写成 ✅。
  2. 示例即实测：文档里的每个代码示例在发布前编译通过并实机运行过；做不到的写「UNKNOWN / NOT RUN」，绝不编造结果。
  3. API 先核实再落地：每个公开 API 以目标 Build 程序集反编译核实签名为准，不以记忆或旧文档为准（知识库铁律）。
  4. 不靠魔法：框架 UI 全部走引擎公开 API（Widgets / GUI / ContentFinder / Event）；不用 Harmony 补丁画 UI、不用反射戳私有字段——冲突面最小化。
  5. 降级诚实：未装 / 低版本 RUIF 时消费 Mod 走原生降级路径，且该路径必须是实机测过的。当前状态：NOT RUN —— "禁用 RUIF"实机测试待执行；未测前不对外宣称降级成立。
一句话总结：RUIF 能在环世界引擎里 100% 诚实落地的是「原版 UI 能力面 + 其上的组合、布局、调试」——这部分没有任何失真；圆角/字体/图表这三类有代价的替代实现会逐项标注代价；引擎做不到的（自动 diff、模糊后处理、原生控件、多线程 UI、松散字体）框架明确不承诺，也永远不会偷偷用 ⚠️ 冒充 ✅。
