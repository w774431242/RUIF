## 2. 可行性评估

### 2.1 组件分级统计（来自图鉴标注）

| 等级 | 数量 | 说明 |
|---|---|---|
| ✅ 纯原生 | **约 137** | 全部可由已核实公开 API 实现，零妥协 |
| ⚠️ 有代价 | **约 15** | AvatarPawn · GearSlots · InventoryGrid（贴图）；Charts · RelationGraph · ProgressRing 弧形 · MiniMap（折线或 RenderTexture）；RichTextLine · MultiLineEditor · PathField · HotkeyBind · CommandPalette · ScrollFadeHint · OverflowFade |
| ❌ 不承诺 | 0 | 图鉴内已剔除（自动 diff、模糊后处理、原生控件、多线程 UI、松散 TTF） |

### 2.2 三维可行性判定

| 维度 | 判定 | 依据 |
|---|---|---|
| **技术可行性** | 🟢 **可行** | 137 件所依赖的官方 API **已全部反编译核实**（`API签名核实清单.md` 24 条，含 5 处命名空间纠正）；绘制技法在参考实现中已有 400+ 处实机调用验证 |
| **工程可行性** | 🟡 **有条件** | 工程骨架已通（0 错 0 警 + 可加载）；但**验证闭环未建立**（无单测、无游戏内 Gallery、无示例消费 Mod）——直接堆组件会失控 |
| **规模可行性** | 🟡 **需分批** | 152 件一次性落地必然失控；须按「原子 → 组件 → 交互」分 6 步，每步可验收 |

### 2.3 关键前置（必须先定，否则编码期反复）

1. **`Draw.Scope` 语义**：栈式压栈/出栈的开销模型、嵌套规则、异常安全（`using` + `try/finally`）；
2. **Layout API 形态**：`VStack/HStack/Grid/Split` 的构建-测量-绘制三段式，以及 Dirty 复用失效规则；
3. **主题令牌数值**：Vanilla / Dark 两套的具体色值（当前只有"贴合原版"的描述，需落数字）；
4. **组件命名与目录**：`RUIF.Components.*` / `RUIF.Layout.*` / `RUIF.Theme.*` 的最终命名空间与文件切分；
5. **验证形态**：游戏内 Gallery 窗口（逐件可交互）+ 单测工程（布局/令牌/截断/解析器）。

> 结论：**技术可行、工程需先补全验证闭环、规模必须分批**。v1.0 交付 ✅ 件（约 137），⚠️ 件（约 15）推 v1.1 并先做原型。

## 3. 逐步落地方案（S0–S6）

| 步骤 | 内容 | 相对规模 | 验收门禁 |
|---|---|---|---|
| **S0 验证闭环** | 示例消费 Mod 工程 + 单测工程 + 同步哈希脚本 + Changelog | S | 编译 0/0；示例 Mod 可加载；单测可运行 |
| **S1 内核 I1** | `Draw.Scope` + Layout + Theme 令牌（Vanilla/Dark 数值）+ 布局原子 | M | 布局单测；grep 无裸 `GUI.color`；Gallery 布局示例实机 |
| **S2 原子层 I2** | A0 原子 42 件（4 小批） | L | Gallery 原子页逐件可交互；CJK 截断/22f 行高实机校准 |
| **S3 组件层 I3** | B 输入 28 + C 数据纯 ✅（≈34） | XL | **用 G 预设 ≥2 页复刻成功**（页面验收，非逐件打勾） |
| **S4 交互扩展 I4** | D 反馈 17 + E 导航 12 + 第三方注册 + 焦点仲裁 + Gallery 完整版 | L | 多主题实机切换；键盘导航；焦点冲突回归 |
| **S5 收口 I5** | API 冻结 + SemVer + Changelog + Workshop/GitHub + 语言子包 | M | 示例 Mod 接入；禁用 RUIF 降级实测；两区哈希一致 |
| **S6 v1.1** | ⚠️ 素材/算法件（Charts/RelationGraph/环形/MiniMap/多行编辑/路径） | M | 每件先原型，通过才进主线 |

> 规模标记仅为**相对量级**（S<M<L<XL），不做工期承诺。

## 4. 各步详述

### S0 · 验证闭环（最高优先级，未完成则后续免谈）
- **交付**：①示例消费 Mod 工程（`RUIF.Sample`）——验证"引用 dll 但不内嵌"接入模式 ②单测工程（NUnit，net48）③两区同步 + `Get-FileHash` 脚本 ④Changelog 建立
- **风险**：无验证 = 无法判断"改好没有"，组件越多越失控
- **门禁**：示例 Mod 编译通过且可加载；单测工程可运行；同步脚本哈希校验通过

### S1 · 内核（I1）
- **交付**：`Draw.Scope`（`Color` / `Enabled` / `Clip` / `Font` / `Anchor` 五个作用域）+ `Layout`（VStack/HStack/Grid/Split/ScrollView/Spacer）+ `Theme`（Vanilla/Dark 令牌 + `Register`/`Apply`）+ 布局原子（`AspectBox`/`AnchorFrame`/`Spacer`/`SectionFrame`）
- **明确不做**：任何业务组件

### S2 · 原子层（I2，42 件，分 4 小批）
1. 文本原语 6：`FormattedNumber` `TimeStamp` `UnitLabel` `RichTextLine`⚠️ `Typewriter` `SubtitleLine`
2. 几何/状态 11：`SectionFrame` `CornerFrame` `GradientRule` `RuleWithLabel` `Watermark` `InsetPanel` `PulseDot` `StatusGlyph` `LoadingSpinner`（`DrawTextureRotated` 已确认存在 → ✅）`ScrollFadeHint`⚠️ `ExpandCaret`
3. 布局视觉 6：`AspectBox` `AnchorFrame` `Swatch` `GradientBar` `OverflowFade`⚠️ `PinBadge`
4. 工坊实证 19：表格原子族 5 · 面板原子族 4 · 交互原子族 4 · 进度容量 3 · 杂项 3

> **先原子后组件**的理由：上层 68 件的单位排版/时间格式/状态点/截断/展开箭头可全部塌缩为原子引用，总量下降且一致性更高。

### S3 · 组件层（I3，B 28 + C 纯 ✅≈34）
- 输入：B1 8 + B2 8 + B2+ 12（含 `PaintStroke` / `PriorityGrid` / `TimetableMatrix` 工坊三件套）
- 数据：C1 14（不含 Charts/RelationGraph/MoodGauge 弧形态）+ C2 12 + C2+ 14
- **验收方式**：用 **G 预设 ①总督仪表盘 ②殖民者档案** 两个页面复刻 —— 搭不起页面 = 组件不合格

### S4 · 交互扩展（I4）
- D 反馈 17（含 `AlertBlinker` 分级脉冲、`CriticalOverlay` S0 遮罩、`UndoToast`）
- E 导航 12（含 `TimeSpeedControl` / `LayerSwitch` / `NavBackStack`）
- 第三方主题/组件注册、`CommandPalette` / `HotkeyBind` **焦点仲裁**（先独立原型验证再并入）
- Gallery 完整版（逐件可交互 + 三档代码）

### S5 · 收口发布（I5）
API 冻结 + SemVer + `[Obsolete]` 过渡 + Workshop/GitHub + 语言子包（借鉴 RimHUD 机制）+ 示例消费 Mod + 降级路径实测

### S6 · v1.1 素材件
`Charts` 折线 · `RelationGraph` · `ProgressRing` 弧形 · `MiniMap`（RenderTexture 原型）· `MultiLineEditor` · `PathField` —— **每件先原型，通过才进主线**

## 5. 风险与缓解

| # | 风险 | 缓解 |
|---|---|---|
| R1 | 验证闭环缺失就堆组件 | **S0 未完成不进 S1** |
| R2 | 主题令牌无数值导致各组件各自取色 | S1 一次性落定 Vanilla/Dark 全部色值，组件只引用令牌 |
| R3 | 焦点仲裁（CommandPalette/HotkeyBind）与游戏快捷键冲突 | S4 内独立原型验证后再并入 |
| R4 | 组件体量失控（想一次做全 152） | 严守 v1.0 = ✅ 件；⚠️ 全推 v1.1 |
| R5 | 硬编码文案触 GOV-010（EXC-001 已登记） | I1 起全部 Keyed + Languages，关闭 EXC-001 |
| R6 | 每帧分配导致 GC 卡顿 | 热路径零分配纪律 + GATE-PERF 复核（S3/S4 各一次） |

## 6. Gate 计划

```text
S0 → GATE-TEST（编译/示例加载/单测可运行）
S1 → GATE-ARCH + GATE-TEST + GATE-UI（组件不持持久状态）
S2 → GATE-UI + GATE-LOC（Keyed，关闭 EXC-001 进度）
S3 → GATE-UI + GATE-PERF + GATE-TEST（页面复刻实机）
S4 → GATE-UI + GATE-PERF + GATE-LOC
S5 → GATE-REL（版本/Changelog/回滚/降级实测）
```

## 7. 结论

**可行，但顺序不能变**：`S0 验证闭环 → S1 内核 → S2 原子 → S3 组件（页面验收）→ S4 交互 → S5 发布`，v1.0 只交付 ✅ 件（约 137），⚠️ 件（约 15）留 v1.1 并先原型。跳过 S0 直接写组件是本次评估识别出的**最大风险**。
