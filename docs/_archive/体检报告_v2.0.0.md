## 3. 已修项（含反编译证据）

### 3.1 三处"alpha 承诺"未生效（同一根因家族）

| 方法 | 症状 | 根因 |
|---|---|---|
| `FeedbackAtomsB.UndoToast(rect, action, alpha)` | 淡出无效 | 用 `GUI.color = tint` 做整体淡出 —— **两条路径都会覆盖它**：<br>① `Widgets.DrawBoxSolid` 内部是「存 → 设为传入色 → 画 → 还原」（ilspycmd 实证）；<br>② `Draw.Label` 自带 Color 作用域 |
| `FeedbackAtoms.Toast(rect, title, sub, level, alpha)` | 淡出无效 | **完全没用 `alpha`**（注释写着"alpha 由 FeedbackFmt.ToastAlpha 驱动"） |
| `FeedbackAtomsB.ActionFeedback(rect, ok, alpha)` | 微反馈不淡出 | **完全没用 `alpha`**（注释写着"alpha 由调用方按 TTL 驱动"，实现固定 0.18f） |

**修法**：一律**把 alpha 乘进颜色**（`Draw.WithAlpha`），不再触碰全局绘制状态。

> 这三条是典型的"**注释承诺 > 实现**"缺陷：文档说会淡出、调用方照文档传参，实际毫无效果 —— 正是"体检"才会暴露的那类问题（编译、单测、发布门禁都发现不了）。

### 3.2 全局绘制状态泄漏风险

`UndoToast` 原来手写 `GUI.color = … / GUI.color = prev`，**没有 try/finally**：`Draw.Box` 一旦抛异常，`GUI.color` 会永久留在 tint 状态 → 染色泄漏到整个游戏的 UI。已在 3.1 的修法中彻底移除全局状态写入（现在框架内除 `Draw` 作用域外**零处**写 `GUI.color`，脚本可断言）。

### 3.3 `[StaticConstructorOnStartup]` 路径的异常外溢

`RUIFSettings.ApplyFromDefs()` 的文档承诺"永不抛异常、永不阻断加载"，但实现**没有 try/catch**：它由静态构造器触发，一旦抛出会导致该静态类型**初始化失败**，后续任何访问都抛 `TypeInitializationException`，风险外溢到其他 Mod。

**实测触发的具体情形**（由本轮新增单测发现）：在非 Unity 宿主（NUnit）里，`Verse.Log.Message` 内部调用的 `UnityEngine.StackTraceUtility.ExtractStackTrace()` 是 **ECall 方法**，会抛 `SecurityException`。

**修法**：① 整体 try/catch；② 静态构造路径上的日志改为容错包装（`TryLogMessage/TryLogWarning`，日志本身不可用时静默）。同时把"单测环境禁用 `Verse.Log`"记为项目级约束。

## 4. P1 · 组件层中文硬编码 67 处（待 PM 决策）

### 4.1 事实

- 位置：`Source/Components/` 15 个文件 + `Source/Config`、`Source/Core`（后两者为 0）。
- 分布（前 12）：`OfficialFmt`8 · `OfficialDataAtomsC`7 · `FeedbackAtomsB`6 · `NavAtomsB`6 · `InputPlusAtoms`6 · `DataExAtoms`4 · `OfficialDataAtomsB`4 · `NavAtoms`4 · `FeedbackAtoms`4 · `InputAtoms`3 · `MiscAtoms`3 · `TableAtoms`3，另 5 个文件各 1–2 处。
- **影响**：任何语言环境下，消费者调用这些组件都会看到中文 —— 例如 `TableAtoms.DensitySwitch` 的「紧凑/标准/舒适」、`ProgressAtoms.ZoomIndicator` 的「缩放/适配」、`InputAtoms` 的「开/关」、`OfficialFmt.RelationLabel` 返回的「同盟/友好/中立/敌对/死敌」。
- **纠正上一轮结论**：v2.0.0 关闭 EXC-001 时说的是"随包不再有硬编码界面文案"——那只覆盖了 Gallery（`DevTools`）。**组件层从未被扫描**，本报告予以纠正并重新登记为 EXC-002。

### 4.2 两类，处置方式不同

| 类 | 说明 | 处数 | 例子 |
|---|---|---|---|
| **A 类·语义返回值** | 函数**返回值就是给 UI 显示的文本**；消费者连覆盖的机会都没有 | **9**（2 文件） | `OfficialFmt.RelationLabel` 五档、`OfficialFmt.EtaLabel`（剩余 N 天/已到期）、`NavFmt.RelativeTime`（刚刚） |
| **B 类·组件自绘文案** | 组件自己画的按钮/标签/提示 | **58**（15 文件） | `ConfirmDialog`「确认/取消」、`UndoToast`「已/撤销」、`DensitySwitch` 三档、`NavBackBar`「（栈深 N）」、`KeyConflictHint` |

### 4.3 三个方案（建议 C）

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A 框架 Keyed 化** | 新增 `RUIF.Comp.*` 键（中英随包），组件内 `.Translate()` | 一次到位，所有消费者受益；键对称/死键已有门禁可保 | 消费者**无法定制**文案；框架替所有人定了 UI 用词 |
| **B 调用方传文案** | 把文案变成参数/重载（`ConfirmDialog(rect, okLabel, cancelLabel, …)`） | 职责最正确（框架不管文案） | ~20 处公共签名变更（v2.0.0 刚承诺 SemVer → 需再走主版本）；调用方全部要改 |
| **C 混合（建议）** | ① A 类改为**返回语义**（枚举/结构，由调用方渲染）；② B 类加**可选文案参数**，默认走 Keyed（框架给中英，调用方可覆盖） | 兼顾正确性与可用性 | 工作量最大（约 1 人日），且 A 类仍属 API 变更 |

> 建议顺序：**先做 B 类 Keyed 化（58 处，无 API 变更，可当补丁发布）**，A 类语义化并入下一个主版本。

### 4.4 实际处置（v2.1.0，2026-09-10）

最终采取了**"A 类语义化 + 全量 Keyed"合并方案**，一次做完，代价可控：

| 决策点 | 结论 | 理由 |
|---|---|---|
| A 类（9 处语义返回值） | 新增纯语义 API：`RelationBand`/`RelationBandOf`、`TimeBucket`/`TimeBucketOf`；文案函数签名不变、内部改走 Keyed | 消费者拿到语义后可自行渲染；**同时保住离线可测性**（否则单测必须调 `Translate`，而离线无语言数据会抛异常） |
| B 类（58 处组件自绘文案） | 直接改走 Keyed，键命名空间 `RUIF.Comp.*`（60 键，中英随包） | 无 API 签名变更；参数化文案的默认值改 `null` 后回退 Keyed（源码级兼容） |
| 参数化文案的 API | 走 `Translate(NamedArgument)`（占位符 `{0}`/`{1}`） | 1.6 里 `Translate(this string, params object[])` 已 `[Obsolete]`（CS0618）；`NamedArgument` 有 int/float/string 隐式转换。编译 0 警即为证据 |
| 版本 | **v2.1.0**（次版本） | 只新增 API、无删除/改名 → 符合 SemVer |
| 单测调整 | 3 个断言文案的用例改为断言**语义**（并补边界值 75 / 74.9 / 59.9s / 60.1s）；`EtaLabel_Formats` 删除 | 文案正确性移交门禁的「键覆盖 + 中英键对称」两道检查 |
| 新增门禁联动 | 第 5 道键命名空间扫描扩展为 `RUIF.(UI\|Comp).` | 否则新键会被漏检（门禁自身的覆盖面相随演进） |

## 6. 已核实为"可接受 / 误报"的项（避免后人重复怀疑）

### 6.1 组件层 `Find.WindowStack.Add(new FloatMenu(...))` ×3

`InputPlusAtoms` / `NavAtoms` / `NavAtomsB` 各一处，用于**官方原生下拉菜单**（FloatMenu 是引擎唯一的下拉路径）。
- 判定：**受控例外**——它是 UI 基础设施而非业务状态；但确实让"组件完全不依赖游戏环境"这一理想打了折扣（无法脱离游戏单测）。
- 附带核实：三处都在**点击分支**内（`if (!Widgets.ButtonInvisible(rect) … ) return` / `if (Widgets.ButtonText(...))`），**不是每帧分配** ✓。

### 6.2 容器分配 7 处（全部非绘制路径）

| 位置 | 判定 |
|---|---|
| `InputPlusFmt.HasConflict/ConflictCount` 的 `new HashSet` | 纯计算函数，调用方按需（改键时）调用 → 可接受（可选优化：静态复用） |
| 三处 `new List<FloatMenuOption>()` | 点击分支 → 可接受 |
| `NavAtoms.TreeNode.Children` 惰性 `new List` | 调用方持有的数据结构，一次性 → 可接受 |
| `NavAtomsB.NavStack.entries` | 构造时按 `NavFmt.StackLimit` 预分配，**有界** → 可接受 |

### 6.3 静态可变集合 2 处

- `Theme.registry`：仅 `Register` 增长（框架 2 个 + 第三方/XML 注册）→ 属于**设计上的扩展点**，无界但受控。
- `RUIFSettings.warnings`：**有 32 条上限保护**（坏配置不刷爆日志）。

### 6.4 脚本误报（已修脚本）

- `TreeNode.Tag` 行尾注释里的 "18 杀"/"5491 殁" 曾被算作硬编码 → 已给 `health_check.ps1` 加"剥离行尾注释（按引号奇偶判定，不误伤字符串内 `//`）"，67 处为修正后真实值。
- `README.md` 出现 "DevTools/Gallery" 属**归档说明**（§3 目录树标注 `_archive/DevTools_Gallery`、§8 记录已关闭），非操作性指引 → 误报。
