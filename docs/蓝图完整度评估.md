# RUIF 项目蓝图完整度评估

> 评估日期：2026-09-08 · 评估对象：RUIF 全部设计文档（v0.3 草案，无代码）
> 评估口径：设计蓝图本身的覆盖度与内部一致性，不含"是否已编码"（编码属于 I1，设计阶段无代码为预期）

---

## 0 · 总体结论

**设计愿景、架构分层、RW 1.6 约束吸收、诚实性（可行性审计/不失真承诺）四个维度高度完整；可执行性硬细节（布局执行模型、状态归属、性能机制、默认令牌值、测试闸门、注册命名空间）存在 P0/P1 缺口。**

整体完整度约 **78%**。属"设计成熟、工程待收敛"。落地风险高度集中在三处：**L4 布局执行模型**、**状态/持久化生命周期**、**零分配/Dirty 机制**——这三处恰好是方案自述"最关键"的 L4 与 RUI 评估反复警告的雷区，目前仍是手绘级描述。

## 2 · 已充分覆盖（强项）

- **范式定调正确**：即时模式 + 轻量布局助手，明确不走保留模式虚拟树（吸收 RUI 评估 §2.1 的致命风险）。
- **RW 1.6 坑内建 L0**：RadioButton 无 Group、ButtonText 无 disabled、GUI.color 配对、TipSignal 秒数、CJK 22f、DrawBoxSolid 重置色——六条硬约束已落文字。
- **三档 API 与 Adapter 层**：直接吸收 RUI 评估建议，DX 梯度和版本隔离都有。
- **集成路径可落地**：框架 Mod 模式（单份 dll）、modDependencies + loadAfter、版本探测 `RUIF.Api.IsAvailable` + 原生降级——这是多数社区框架缺的务实一环。
- **可行性审计诚实**：✅/⚠️/❌ 三级且"⚠️ 永不写 ✅"、"示例即实测"、"API 先反编译核实"——失真风险被主动压制。
- **组件图鉴有工坊实证背书**：PriorityGrid/NodeGraph/DockHost 等均标"工坊实证"，非臆想。

## 3 · 关键缺口与风险

### P0（不收口会卡死 I1/I2）

- **G1 · L4 布局执行模型自相矛盾（最致命）**
  方案 §4 示例是**两阶段**：`root.Add(...)` 收集 → `root.Build()` 算 Rect 并绘制；
  接入指南 §2 示例是**一阶段**：`using(col)` 块内 `col.Button(...)` 直接绘制并返回 `bool` 点击。
  两种模型对"组件实例是否存在""点击如何返回""Rect 何时算"给出相反答案。IMGUI 无保留树，必须二选一并在 I1 前冻结。这是方案自述"最关键"的层，当前不可编码。

- **G2 · 状态归属与读档存活未定义**
  RUI 评估 §2.3 把"State 生命周期"列为死活问题。RUIF 现状：L5 说"数据由调用方注入"；接入指南 §0 说"有状态组件你 new、你持有，别存 Window 里"。但**没说存哪**：GameComponent？静态字段？如何跨窗口重开存活？如何随存档 Scribe 持久化？蓝图缺"状态所有权 + 持久化"一章，而这是框架对消费 Mod 的承诺之一。

- **G3 · 零分配 / Dirty 复用机制为空**
  方案定调"Layout 算一次 Rect + Dirty 复用"，接入指南 ⚠️ 行写"布局缓存 + Dirty 标记 + 对象复用"。但**无具体设计**：缓存以何为键（窗口+inRect？）、何时失效、Build 每帧调还是 Dirty 才调、对象池形态。这是"每帧零分配"铁律能否兑现的核心，目前是口号级。

### P1（I2 前需补齐）

- **G4 · 默认 Vanilla 主题令牌值未定义**：§4 L1 称内置 Vanilla（默认）+ Dark + 示例主题，但全仓**无一张 Vanilla 调色板令牌表**。"禁止 new Color"依赖令牌单一真源，而真源本身未落值。
- **G5 · 注册 ID 命名空间 / 碰撞策略缺失**：扩展点 `Theme.Register(id,...)`、`组件注册进 Gallery` 用裸字符串 id，两 Mod 取同名即冲突，无前缀/命名空间约定。
- **G6 · 主题 Apply 全局 vs 多 Mod 共存**：§5 `RUIF.Theme.Apply(id)` 是全局静态；多消费 Mod 各 Apply 不同主题会互相打架，无 per-window 作用域。
- **G7 · 键盘导航 / a11y 算法缺失**：L5 列"容器 Tab/方向键焦点环"，但 IMGUI 无保留树，焦点索引存哪、如何遍历——未设计。
- **G8 · 测试策略薄弱**：§12 提 NUnit + 模拟事件，无覆盖目标、无 CI、无"示例即实测"的回归载体（目前 0 代码，所有示例均未实测，虽已诚实声明）。

### P2（可后补）

- **G9 · 无 changelog 文件**：方案把 changelog 定为契约真源，但仓库无此文件（预期 I1 建）。
- **G10 · 错误处理细节**：Apply 未注册回退默认已有；但畸形 palette（null 色）行为未定义。
- **G11 · Languages 目录**：接入指南 §4 称内置文案走 Keyed `RUIF.UI.*` 随 Languages 提供，但 RUIF 当前无 Languages 目录（预期 I3）。

## 4 · 跨文档一致性问题

| 冲突点 | 底层UI框架方案 | 接入指南与引擎可行性审计 | 影响 |
|---|---|---|---|
| Button 签名 | §7 `RUIF.Button("开始")`；§4 `Button(rect,label).OnClick(action)` | §3 `RUIF.Button(rect,"开始")`；§2 `col.Button("确认")` 返回 bool | 三处三种形状，消费 Mod 无法对齐 |
| VStack 用法 | §4 `Layout.VStack(outer,gap).Add(...)` + `root.Build()`（两阶段） | §2 `RUIF.VStack(inRect,gap)` using 块 + `col.Button()`（一阶段） | 执行模型相反（见 G1） |
| 布局命名空间 | §6 `RUIF.Layout.VStack` | §2 `RUIF.VStack`（无 Layout 前缀） | 命名空间不一致 |
| 组件归属命名 | L3 称 `Controls` 层 | API 直接用 `RUIF.Button/Card`（无 Controls 前缀） | 层名与 API 名脱节 |

## 5 · 范围与优先级风险

- **图鉴范围失控**：组件设计图鉴累计 **152 组件 + 12 版式 + 12 页面预设 + I 节极量扩展**（PriorityGrid/NodeGraph/DockHost/TimetableMatrix 等工坊大件）。但路线图 I2 仅承诺"Button/Card/Pill/Badge/ProgressBar/Table/Sidebar 等"小核心。
- **缺 catalog→roadmap 映射**：虽 H 节有"迭代分级映射"，但单个组件未打 I1–I4 标签，易陷入"先画完 152 件再写代码"的分析瘫痪（RUI 评估 §2.4 已预警）。
- **建议**：在图鉴每个组件上加"目标迭代"标（I2 核心 / I3 / backlog），把 152 件显式降级为"候选池"，I2 只锁 ~12 件核心。

## 6 · 落地前必须收口清单（I1 闸门）

1. **冻结 L4 执行模型**（G1）：选定两阶段或一阶段，全文档统一签名。
2. **补"状态所有权 + 持久化"一章**（G2）：明确有状态组件存 GameComponent/静态、跨窗口存活、Scribe 策略。
3. **补 Dirty/缓存/对象池设计**（G3）：给出缓存键、失效条件、Build 调用时机。
4. **定义 Vanilla 默认令牌表**（G4）：落地"禁止 new Color"的真源值。
5. **统一跨文档 API 签名**（§4 表）：Button/VStack/命名空间三处冲突消掉。
6. **定注册 ID 命名空间规则**（G5）与 per-window 主题作用域（G6）。
7. **建 changelog 骨架 + 测试回归载体**（G9/G8）。

## 7 · 一句话建议

蓝图在"想清楚做什么"上已接近可发布质量；在"想清楚怎么算对"上（布局执行、状态、性能）还差最关键的一跃。建议 I1 前先写一份 **《L4 执行模型 + 状态/性能契约》补篇**，把 G1–G3 钉死，否则 I1 一动手就会在"Build 每帧重算还是 Dirty 才算""点击 bool 还是回调"上反复返工。
